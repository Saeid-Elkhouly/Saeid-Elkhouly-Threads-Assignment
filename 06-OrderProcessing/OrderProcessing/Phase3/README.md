```csharp
{
    await _orderRepository.SaveAsync(order);

#pragma warning disable CS4014
    _emailService.SendConfirmationAsync(order, customer);
#pragma warning restore CS4014

    Console.WriteLine("Order processing finished");
}
```

Because the email operation is not awaited, `ProcessOrderAsync` does not wait for the email to finish before printing the message and returning.

### 2. What happens if the email is still being sent?

The email operation starts, but the processing method continues immediately. It can print `Order processing finished` and return while the email is still pending.

If the console application exits before the email operation completes, the process may terminate before the email is sent successfully.

Run `FireAndForgetDemo.RunControlledScenariosAsync(store, order, customer)` to observe a gated email task. The supplied `JsonFileStore` receives the demo order upserts, so use an isolated data directory. The harness holds the email task open until after the broken method returns and then triggers a deterministic provider failure.

**Observed controlled output for the broken method:**

```text
Broken method: email remains pending after the method returns.
Order processing finished
Observed: ProcessOrderAsync returned while email was still pending.
Harness observed the later email failure: Controlled email failure
The broken processing method did not observe that email exception.
```

The harness observes the discarded email task separately to report the later failure. The broken caller does not receive that exception through `ProcessOrderAsync`. In an ordinary process, an unobserved task exception is not guaranteed to appear on the console. If the application exits while the operation is pending, the email may never finish.

### 3. What happens if the email operation throws an exception?

If `SendConfirmationAsync` throws an exception, its returned `Task` becomes faulted. Since the task is not awaited or otherwise observed by the processing method, the caller does not receive that exception through `ProcessOrderAsync`.

The order-processing method can therefore appear to have succeeded even though sending the confirmation email failed. An unobserved task exception is not guaranteed to appear on the console; its behavior depends on the runtime and whether the task is observed elsewhere.

### 4. Fix the implementation

The fix is to await `SendConfirmationAsync`.

```csharp
public async Task ProcessOrderAsync(Order order, Customer customer)
{
    await _orderRepository.SaveAsync(order);
    await _emailService.SendConfirmationAsync(order, customer, CancellationToken.None);

    Console.WriteLine("Order processing finished");
}
```

Now, the method waits for the email operation to complete before printing the message and returning. If email sending fails, the exception propagates to the caller, which can handle it with `try`/`catch`.

**Observed controlled output after the fix:**

```text
Fixed method: caller waits for successful email completion.
Observed: ProcessOrderFixedAsync is still pending while email is pending.
Order processing finished

Fixed method: caller observes an email failure.
Awaited caller observed the email failure: Controlled email failure
```

The broken example is intentionally fire-and-forget. The fixed version awaits the same service call and propagates its exception to the awaiting caller. `await` is necessary when later work depends on completion, the result matters, or the caller must observe failures. Fire-and-forget is acceptable only when a managed background-work mechanism owns completion, shutdown, retries, and error reporting. `async void` is dangerous for ordinary methods because callers cannot await it or catch its exceptions; it is acceptable for event handlers when required by the event API and the handler catches errors internally.

### 5. When is `await` necessary?

Use `await` when the current operation must finish before the method continues, when its result is needed, or when its exceptions must be observed and handled by the caller.

For example, if order processing must wait for the confirmation email and continue only after it succeeds, it must await the email task.

## Storage and JSON format

`JsonFileStore` writes UTF-8 JSON arrays with indented, camel-case property names and string-valued enums. The collection files are `customers.json`, `products.json`, `coupons.json`, `incoming_orders.json`, `orders.json`, `payments.json`, `emails.json`, and `email_retry.json`. Phase 2 also writes invoice text files under `invoices/` and report JSON under `reports/`.

Within one process, a path-keyed `SemaphoreSlim` protects each file's read/modify/write operation. Writes serialize to a unique temporary file in the same directory and replace the destination after the write completes, so callers do not see a partially serialized JSON collection. This lock is process-local; it is not a cross-process file lock.

| Phase / measurement | Observed result |

| Phase 1 validation | Sync 35.4 s; async 53.9 s (20 orders) |
| Phase 2 Order #1 pricing | Sequential 4.15 s; concurrent 3.42 s |
| Phase 2 order processing | 9.76 s (20 orders) |

| Phase 4 email re-send | 4.11 s; maximum concurrency 4 |

Phase 2 and Phase 3 comparisons show that asynchronous I/O does not make an individual request's underlying wait shorter. It lets a thread do other work while a request waits. A synchronous version with 1,000 orders would require many blocked dedicated threads, with higher memory and scheduling costs. Database, file, and API calls are I/O-bound, so asynchronous waiting improves throughput without a thread per request. Fraud scoring is CPU-bound and can benefit from parallel execution across available cores. Parallel CPU work consumes cores simultaneously; concurrent asynchronous I/O overlaps waiting operations.
